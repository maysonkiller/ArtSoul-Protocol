## Scope and implementation

The founder requested reversible favorites for art, auctions and NFTs after
Phase A. Watching already records a discovery signal and contributes to ranking;
reusing it would silently change that behavior. Saved is a separate private list.

- One identity is chain + core registry + artwork ID. Re-auction and later mint
  retain one save. An auction ID or token ID is not substituted for the artwork.
- A shared bookmark control sits over card media on home, gallery and profile,
  plus the artwork header. Existing Donate / Report / Creation transaction menu
  is unchanged. Both themes use existing variables. At narrow mobile widths the
  controls occupy separate positions; metadata spacing remains unchanged.
- Only the owner sees the Saved profile tab. Reads and writes use the existing
  wallet session plus an expected-wallet header. Wallet changes, auth changes,
  page hide and restored navigation clear private in-memory state. No private
  list is written to browser storage or exposed on public profiles.
- Adds/removals are idempotent. UI waits for the acknowledgement; failed writes
  never show successful saves. Late reads cannot overwrite a newer write, restore
  a removed card, repaint another wallet's list, or replace a newer successful
  list with an old failure. An open list refreshes after confirmed changes.
- Card state is read in batches of at most 50 IDs (API maximum 200). Lookup
  requires and echoes the configured deployment. List pages use an exact bigint
  cursor, 20 entries, and at most four simultaneous existing public projections.
  Current visibility/existence is read fresh; hidden/missing/old-deployment
  entries expose no artwork content but can still be removed.
- The new table uses RLS, no client-role policies, revoked client table/sequence
  permissions and explicit service grants. This works without Supabase's old
  implicit grants. The server derives the owner from its signed session.
- `ARTSOUL_SAVED_ENABLED` defaults off. No contract, economic, public Trust,
  email subscription, OAuth or staff-authorization changes; no new dependency.

## Explicit interpretations and remaining boundaries

Canon sections touched: Bible §5 provenance, §6 discovery, §11 privacy and
moderation, §13 visual rules / document 16, and §17 Phase B. No frozen
architecture amendment is needed.

1. Personal favorites are private and rank-neutral, with no email opt-in.
2. The first slice requires wallet sign-in. Optional guest-local saves and an
   explicit merge are deferred; no implicit cross-wallet import is implemented.
3. The active Base Sepolia deployment supports adds. A saved old deployment is
   retained as unavailable and removable. Future collection identities need
   explicit mapping when actual collection publishing is activated.
4. Page sizes/concurrency are implementation bounds, not economics or entitlement.
5. Existing projection tables are still keyed by chain/artwork, not registry.
   Before rotating the core, reconcile their source and keep Saved disabled
   until that mapping is verified. This feature does not make the indexer
   deployment-aware. Cold pages can require multiple exact projections; the
   first implementation favors correct older saves over truncating to the
   latest 200-card feed. Measure actual latency before widening beta use.

6. Roll back presentation/API availability by setting the flag false and
   redeploying. Retain the private table and bookmarks; do not drop data.
